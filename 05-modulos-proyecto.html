Terraform · Cheatsheet 05

Módulos y estructura de proyecto

Un módulo es una carpeta de .tf que se reutiliza como si fuera una función: recibe variables, crea recursos y devuelve outputs.

Cómo funciona un módulo Crear uno Fuentes Versiones Estructura de proyecto Buenas prácticas

Términos de esta página

Módulo
Una carpeta de archivos .tf que se puede reutilizar, como una función: recibe variables y devuelve outputs.
Root module
La carpeta donde corrés terraform plan. Desde ahí se llaman los demás módulos (“módulos hijos”).
source
De dónde sale un módulo: una carpeta local, el Terraform Registry o un repositorio de Git.
Terraform Registry
El catálogo público (registry.terraform.io) de providers y módulos listos para usar.
Versión / restricción
Qué versiones de un provider o módulo aceptás, por ejemplo ~> 3.0 (“la 3 y sus arreglos”).
Lock file
.terraform.lock.hcl: anota la versión exacta de cada provider usada, para que todos usen la misma.
Entorno
Una copia separada de la infraestructura para un propósito: desarrollo (dev), pruebas (qa/staging), producción (prod).
Tag de Git
Un nombre fijo para un commit (v1.2.0); se usa para versionar módulos guardados en Git.
1

Cómo funciona un módulo

Entradas → recursos → salidas. El que llama solo ve las salidas.

i

Toda carpeta con .tf es un módulo. La que ejecutás con terraform plan es el root module.

i

Los recursos internos se ven en el estado como module.app.docker_container.this.

!

Después de agregar o cambiar un module hay que correr terraform init otra vez.

2

Crear un módulo

Tres archivos alcanzan.

variables.tf

modules/app/variables.tf
variable "nombre" {
  type        = string
  description = "Nombre del contenedor"
}

variable "imagen" {
  type = string
}

variable "puerto" {
  type    = number
  default = 3000
}

main.tf

modules/app/main.tf
resource "docker_image" "this" {
  name         = var.imagen
  keep_locally = true
}

resource "docker_container" "this" {
  name  = var.nombre
  image = docker_image.this.image_id

  ports {
    internal = var.puerto
    external = var.puerto
  }
}
✓

Convención: si el módulo crea uno solo de un tipo, llamalo this.

outputs.tf

modules/app/outputs.tf
output "url" {
  value = "http://localhost:${var.puerto}"
}

output "id" {
  value = docker_container.this.id
}
i

Un módulo bien hecho no configura provider adentro: lo hereda del que lo llama.

3

De dónde sale un módulo (source)

Mismo bloque module, distintos orígenes.

Ejemplos de source

# carpeta local (sin version)
module "app" {
  source = "./modules/app"
}

# Terraform Registry (con version)
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 6.0"
  # ...
}

# repositorio git en un tag
module "red" {
  source = "git::https://github.com/<org>/terraform-red.git?ref=v1.2.0"
}

# subcarpeta de un repo
module "db" {
  source = "github.com/<org>/infra//modules/db?ref=v2.0.0"
}

Varias instancias de un módulo

module "servicio" {
  source   = "./modules/app"
  for_each = {
    chanchito = { imagen = "chanchito:1", puerto = 3000 }
    admin     = { imagen = "admin:1",     puerto = 4000 }
  }

  nombre = each.key
  imagen = each.value.imagen
  puerto = each.value.puerto
}

output "urls" {
  value = { for k, m in module.servicio : k => m.url }
}
i

count, for_each, depends_on y providers también funcionan en module.

4

Versiones de Terraform y providers

Fijá rangos en el código; el lock file fija la versión exacta.

versions.tf

versions.tf
terraform {
  required_version = ">= 1.11"

  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0"
    }
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}
i

source es <organización>/<nombre> en el Registry. Sin organización se asume hashicorp/.

Operadores de versión

RestricciónAcepta
= 3.0.2Solo esa versión
>= 3.03.0 o cualquier mayor (incluso 4.x)
~> 3.03.0 hasta antes de 4.0 (3.x)
~> 3.0.23.0.2 hasta antes de 3.1 (solo parches)
>= 3.0, < 3.5Rango explícito
!= 3.1.0Excluir una versión rota
✓

~> es el más usado: deja entrar arreglos sin saltar de versión mayor.

!

Para subir de versión: cambiás la restricción y corrés terraform init -upgrade. Sin -upgrade se respeta el lock file.

5

Estructura de proyecto

Módulos reutilizables + una carpeta por entorno con su propio estado.

Árbol sugerido

infra/
├── modules/
│   ├── app/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   └── red/
├── envs/
│   ├── dev/
│   │   ├── main.tf          # llama a ../../modules/*
│   │   ├── backend.tf       # estado de dev
│   │   ├── versions.tf
│   │   ├── terraform.tfvars
│   │   └── .terraform.lock.hcl
│   └── prod/
│       └── …                # mismo esquema, otro estado
├── .gitignore
└── README.md
terraform -chdir=envs/dev plan
Ejecuta Terraform sobre la carpeta de un entorno sin hacer cd. Cada carpeta de envs/ tiene su propio estado, así que hay que hacer init en cada una la primera vez: terraform -chdir=envs/dev init.

Carpetas por entorno vs workspaces

Carpeta por entornoWorkspaces
EstadoSeparado, incluso en otro backend/cuentaSeparado, en el mismo backend
Diferencias entre entornosExplícitas en cada carpetaCondicionales con terraform.workspace
Riesgo de equivocarseBajo: la carpeta indica el entornoMás alto: depende de qué workspace está activo
Ideal paradev / staging / prod realesCopias temporales y pruebas

Archivos habituales

main.tfRecursos o llamadas a módulos
variables.tf / outputs.tfEntradas y salidas
versions.tfrequired_version y providers
providers.tfConfiguración de providers
backend.tfDónde va el estado
locals.tf / data.tfCálculos y lecturas
6

Buenas prácticas

Lo que evita sustos en producción.

Código

  • terraform fmt y validate antes de cada commit (o en CI).
  • Versiones fijadas con ~> y lock file en git.
  • Nada hardcodeado que cambie entre entornos: variables.
  • description en variables y outputs: es la documentación del módulo.
  • Etiquetá todo (tags/labels) con proyecto, entorno y gestion = "terraform".

Estado y cambios

  • Estado remoto con bloqueo y cifrado; acceso restringido.
  • Leé el plan entero; desconfiá de -/+ en recursos con datos.
  • prevent_destroy en bases de datos y buckets críticos.
  • Nada de cambios manuales en la consola: generan drift.
  • -target solo para emergencias.

Equipo

  • Plan en cada pull request y apply solo desde main.
  • Estados chicos por dominio (red, datos, apps).
  • Módulos versionados con tags git (?ref=v1.2.0).
  • Herramientas útiles: tflint (linter), checkov o trivy (seguridad), terraform-docs (README de módulos).
