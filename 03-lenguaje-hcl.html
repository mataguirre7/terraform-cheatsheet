El lenguaje HCL

HCL (HashiCorp Configuration Language) es declarativo: bloques con argumentos. El orden de los bloques no importa; Terraform arma el orden según las referencias entre recursos.

Anatomía de un bloque

Tipo, etiquetas y cuerpo con argumentos y bloques anidados.

i

Comentarios: # o // para una línea, /* … */ para varias.

i

Terraform lee todos los .tf de la carpeta como si fueran uno. Los nombres de archivo son solo para ordenarte.

✓

Convención: nombres en snake_case; no repitas el tipo en el nombre (docker_container.chanchito, no …chanchito_container).

Tipos complejos en una variable

variable "servicios" {
  type = map(object({
    imagen = string
    puerto = number
    env    = optional(map(string), {})
  }))
  default = {
    chanchito = { imagen = "chanchito:1", puerto = 3000 }
    monguito  = { imagen = "mongo:7",     puerto = 27017 }
  }
}
i

optional(tipo, default) deja que un atributo del objeto no se pase.

Expresiones

Lo que podés poner a la derecha de un =.

Strings y condicionales

# interpolación
name = "${var.proyecto}-${var.entorno}"

# condicional:  cond ? si : no
replicas = var.entorno == "prod" ? 3 : 1

# heredoc (texto de varias líneas)
script = <<-EOT
  echo "hola"
  echo "${var.entorno}"
EOT

for y splat

# lista → lista
nombres = [for s in var.servicios : upper(s)]

# con filtro
prod = [for s in var.lista : s if s != "test"]

# lista → mapa
puertos = { for k, v in var.servicios : k => v.puerto }

# splat: un atributo de todas las instancias
ids = docker_container.app[*].id

Operadores

5

count vs for_each

Los dos crean varias instancias. La diferencia aparece cuando sacás una del medio.

count

resource "docker_container" "worker" {
  count = 3
  name  = "worker-${count.index}"
  image = docker_image.app.image_id
}

# crear o no crear
count = var.crear_db ? 1 : 0

for_each con set

resource "docker_volume" "datos" {
  for_each = toset(["mongo", "redis"])
  name     = "${each.key}-data"
}
i

Con un set, each.key y each.value son iguales.

for_each con map

resource "docker_container" "svc" {
  for_each = var.servicios
  name     = each.key
  image    = each.value.imagen
}
!

for_each acepta map o set, no listas: convertí con toset().

6

Bloques dynamic

Repetir un bloque anidado a partir de una colección.

Ejemplo: varios puertos

variable "puertos" {
  default = { "3000" = 3000, "9229" = 9229 }   # interno = externo
}

resource "docker_container" "chanchito" {
  name  = "chanchito"
  image = docker_image.app.image_id

  dynamic "ports" {
    for_each = var.puertos
    content {
      internal = ports.key
      external = ports.value
    }
  }
}

Cómo leerlo

  • dynamic "ports": el nombre del bloque anidado a generar.
  • for_each: la colección a recorrer.
  • content { }: el contenido de cada bloque generado.
  • Dentro se usa <nombre>.key y <nombre>.value (acá ports.key).
!

No abuses: si el bloque es fijo, escribilo a mano. dynamic hace el código más difícil de leer.

7

Meta-argumentos

Funcionan en cualquier resource (y varios en module).

depends_on y provider

resource "docker_container" "chanchito" {
  # dependencia que Terraform no puede deducir
  depends_on = [docker_container.monguito]

  # usar una configuración alternativa del provider
  provider = docker.remoto
}

provider "docker" {
  alias = "remoto"
  host  = "ssh://usuario@servidor"
}
i

Si ya usás una referencia (docker_network.app.name), la dependencia es automática: no hace falta depends_on.

lifecycle

lifecycle {
  create_before_destroy = true     # crea el nuevo antes de borrar el viejo
  prevent_destroy       = true     # error si un plan quiere destruirlo
  ignore_changes        = [env]    # no pelear con cambios hechos afuera
  replace_triggered_by  = [docker_image.app.image_id]
}
prevent_destroyPara bases de datos y buckets importantes
ignore_changesAtributos que modifica otra herramienta
replace_triggered_byRecrear cuando cambia otro recurso

Validaciones

resource "docker_container" "chanchito" {
  # ...
  lifecycle {
    precondition {
      condition     = var.puerto > 1024
      error_message = "Usá un puerto mayor a 1024."
    }
  }
}

check "app_responde" {
  data "http" "home" { url = "http://localhost:3000" }
  assert {
    condition     = data.http.home.status_code == 200
    error_message = "chanchito no responde."
  }
}
i

check solo avisa (warning); precondition/postcondition frenan el plan o el apply.

8

Refactorizar sin destruir: moved y removed

Cambiar nombres o soltar recursos quedando registrado en el código.

moved (renombrar)

# renombraste docker_container.app → docker_container.chanchito
moved {
  from = docker_container.app
  to   = docker_container.chanchito
}

# pasar de count a for_each
moved {
  from = docker_container.svc[0]
  to   = docker_container.svc["chanchito"]
}
✓

Sin moved, renombrar = destruir el viejo y crear uno nuevo.

removed (dejar de administrar)

removed {
  from = docker_volume.viejo
  lifecycle {
    destroy = false   # no lo borra, solo lo saca del estado
  }
}
i

Es la versión revisable de terraform state rm: queda en el código y aparece en el plan.
