Terraform · Cheatsheet 04

Variables y estado

Cómo parametrizar la configuración y dónde guarda Terraform lo que ya creó. El estado es lo más delicado de un proyecto: si se pierde o se corrompe, Terraform deja de saber qué administra.

Variables Precedencia Outputs y locals El archivo de estado Bloqueo Backends remotos Secretos y git

Términos de esta página

Variable (input)
Un parámetro de entrada de tu configuración, para no escribir valores fijos (región, nombre, tamaño). Se usa como var.nombre.
.tfvars
Un archivo con valores para las variables (nombre = valor), por ejemplo uno por entorno.
Precedencia
El orden que decide qué valor gana cuando una variable está definida en varios lugares.
Output
Un valor que Terraform muestra al terminar (una IP, una URL) o que un módulo entrega a quien lo usa.
Local
Un valor calculado internamente para no repetir expresiones. Se usa como local.nombre.
Sensitive
Marca que oculta un valor en pantalla. Ojo: en el archivo de estado se sigue guardando en texto plano.
Estado (tfstate)
El archivo JSON donde Terraform anota qué creó y los identificadores reales de cada recurso.
Backend remoto
Guardar el estado fuera de tu PC (un bucket en la nube o HCP Terraform), para compartirlo con el equipo y no perderlo.
Bucket
Un “contenedor de archivos” en servicios de almacenamiento en la nube (S3 en AWS, Storage en Azure, GCS en Google).
Lock (bloqueo)
Marca que impide que dos ejecuciones modifiquen el mismo estado al mismo tiempo.
1

Variables de entrada

Se declaran en variables.tf y se usan como var.<nombre>.

Declaración completa

variables.tf
variable "entorno" {
  type        = string
  description = "Nombre del entorno (dev, qa, prod)"
  default     = "dev"

  validation {
    condition     = contains(["dev", "qa", "prod"], var.entorno)
    error_message = "entorno debe ser dev, qa o prod."
  }
}

variable "mongo_password" {
  type      = string
  sensitive = true      # no se muestra en plan ni en logs
  # sin default: es obligatoria
}

variable "replicas" {
  type     = number
  default  = 1
  nullable = false      # no acepta null
}

Darles valor

terraform.tfvarsse lee solo
entorno  = "dev"
replicas = 2
prod.tfvars-var-file="prod.tfvars"
entorno  = "prod"
replicas = 3
# secretos: por variable de entorno, nunca en un archivo versionado
$env:TF_VAR_mongo_password = "<password>"
terraform plan
PowerShell. En Bash: export TF_VAR_mongo_password=…
i

Si una variable obligatoria no tiene valor por ningún lado, plan te la pregunta por teclado.

2

Precedencia: quién gana

Si la misma variable tiene valor en varios lugares, gana el de más a la derecha.

3

Outputs y locals

Lo que sale y lo que se calcula por dentro.

output

outputs.tf
output "url" {
  description = "Dónde abrir la app"
  value       = "http://localhost:${var.puerto}"
}

output "mongo_password" {
  value     = var.mongo_password
  sensitive = true    # se muestra como (sensitive value)
}
terraform output
terraform output -raw url
Se muestran al final de cada apply y se consultan cuando quieras.

locals

locals.tf
locals {
  prefijo = "${var.proyecto}-${var.entorno}"

  etiquetas = {
    proyecto = var.proyecto
    entorno  = var.entorno
    gestion  = "terraform"
  }
}

# uso
name = "${local.prefijo}-api"
i

Variable = lo que se pasa desde afuera. Local = un cálculo interno para no repetir expresiones.

4

El archivo de estado

terraform.tfstate: un JSON que une cada recurso del código con su objeto real.

Qué tiene adentro

{
  "version": 4,
  "serial": 12,
  "resources": [{
    "type": "docker_container",
    "name": "chanchito",
    "instances": [{
      "attributes": {
        "id": "4f2a9c…",
        "name": "chanchito",
        "env": ["MONGO_PASSWORD=…"]   ← ¡en texto plano!
      }
    }]
  }]
}

Reglas de oro

  • Nunca lo edites a mano: usá terraform state …, moved, import o removed.
  • Nunca lo subas a git: puede tener contraseñas, claves y tokens.
  • En equipo, siempre en un backend remoto con bloqueo.
  • Un estado por entorno (dev y prod no comparten estado).
  • Estados chicos: separá redes, bases y apps en proyectos distintos para limitar el daño de un error.
i

terraform.tfstate.backup es la versión anterior, que se guarda sola en el backend local.

Bloqueo del estado

Evita que dos apply simultáneos corrompan el estado.

6

Backends remotos

Se configuran en el bloque terraform. Después de cambiarlo: terraform init -migrate-state.

AWS S3

terraform {
  backend "s3" {
    bucket       = "<mi-bucket-de-estados>"
    key          = "chanchito/dev/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true   # lock nativo en S3
  }
}
i

use_lockfile reemplaza a la tabla de DynamoDB, que quedó deprecada. Requiere una versión reciente de Terraform (1.11+).

Azure Storage

terraform {
  backend "azurerm" {
    resource_group_name  = "rg-terraform"
    storage_account_name = "<cuenta>"
    container_name       = "tfstate"
    key                  = "chanchito/dev.tfstate"
  }
}
i

El bloqueo usa el lease del blob: viene incluido.

Google Cloud Storage

terraform {
  backend "gcs" {
    bucket = "<mi-bucket-de-estados>"
    prefix = "chanchito/dev"
  }
}

HCP Terraform

terraform {
  cloud {
    organization = "<mi-org>"
    workspaces {
      name = "chanchito-dev"
    }
  }
}
i

Servicio de HashiCorp: guarda estado, bloquea y además puede correr los plan/apply. Pide terraform login.

Configuración parcial

# main.tf: el bloque queda casi vacío
terraform {
  backend "s3" {}
}
# backend-dev.hcl
bucket = "<bucket>"
key    = "chanchito/dev/terraform.tfstate"
region = "us-east-1"
terraform init -backend-config=backend-dev.hcl
Mismo código, distinto backend por entorno. Los backends no aceptan variables: así se parametrizan.

Local (por defecto)

Sin bloque backend, el estado queda en terraform.tfstate junto al código.

  • Ideal para aprender y para la práctica con Docker.
  • No sirve para equipos: no se comparte ni se bloquea entre máquinas.

Secretos y qué subir a git

sensitive solo oculta valores en pantalla: en el estado siguen en texto plano.

.gitignore para Terraform

.gitignore
# providers y módulos descargados
.terraform/

# estado (puede tener secretos)
*.tfstate
*.tfstate.*

# planes guardados
tfplan
*.tfplan

# valores con secretos
*.tfvars
!ejemplo.tfvars

# logs y overrides locales
crash.log
crash.*.log
override.tf
*_override.tf

Qué sí y qué no

Archivo¿A git?
*.tf✓ Sí
.terraform.lock.hcl✓ Sí (versiones exactas de providers)
ejemplo.tfvars sin secretos✓ Sí, como plantilla
.terraform/✕ No
*.tfstate✕ Nunca
*.tfvars con secretos✕ No
✓

Para secretos de verdad: TF_VAR_… en CI, o leerlos con un data source de un gestor (AWS Secrets Manager, Azure Key Vault, Vault).
