Terraform · Cheatsheet 02

La CLI de Terraform

Todos los comandos se ejecutan en la carpeta de los .tf. Los valores en <rosa> se reemplazan. Con OpenTofu, cambiá terraform por tofu.

Instalar Ciclo básico plan y apply init Outputs y consola state e import Workspaces Variables de entorno CI y extras

Términos de esta página

CLI
Usar un programa escribiendo comandos en la terminal. La CLI de Terraform es el comando terraform.
Carpeta de trabajo
Terraform lee todos los .tf de la carpeta donde corrés el comando (o la que indiques con -chdir).
Provider
El plugin que habla con una plataforma (AWS, Docker…). init los descarga.
Backend
El lugar donde se guarda el archivo de estado: tu disco (por defecto) o un almacenamiento remoto.
Plan guardado
Un archivo con el plan calculado (-out=tfplan), para aplicar exactamente eso después.
Lock (bloqueo)
Una marca que evita que dos personas apliquen cambios sobre el mismo estado a la vez.
Importar
Hacer que Terraform empiece a administrar un recurso que ya existía (creado a mano o por otra herramienta).
Workspace
Una forma de tener varios estados separados con el mismo código.
CI (integración continua)
Un sistema que corre comandos automáticamente en cada cambio del repositorio (por ejemplo, GitHub Actions).
Variable de entorno
Un valor que definís en la terminal ($env:NOMBRE = "valor" en PowerShell) y que los programas pueden leer.
1

Instalar y verificar

Es un único ejecutable.

Instalar

winget install Hashicorp.Terraform
Instala Terraform en Windows con winget, el instalador de programas que trae el sistema, y lo agrega al PATH. Cerrá y volvé a abrir la terminal (también VS Code) para que reconozca el comando.
winget install OpenTofu.Tofu
OpenTofu es una copia libre de Terraform, mantenida por la Linux Foundation, compatible con los mismos archivos .tf. Se usa igual, escribiendo tofu en lugar de terraform.
brew install hashicorp/tap/terraform
Instalación en macOS con Homebrew, desde el repositorio oficial de HashiCorp (hashicorp/tap). En Linux, HashiCorp publica paquetes para apt y dnf.

Verificar

terraform version
Muestra la versión de Terraform y, si lo corrés dentro de un proyecto ya inicializado, la de cada provider descargado. Avisa si hay una versión más nueva de Terraform.
terraform -help
terraform plan -help
Sin nada más, lista todos los subcomandos con una línea de explicación. Con un subcomando (terraform plan -help) muestra todas las opciones de ese comando.
terraform -install-autocomplete
Activa el autocompletado con Tab en Bash o Zsh (Linux, macOS, Git Bash). Hay que abrir una terminal nueva después. No funciona en PowerShell.
2

Ciclo básico

En este orden.

Preparar y revisar

terraform init
Descarga providers y módulos, configura el backend. Crea .terraform/ y .terraform.lock.hcl.
terraform fmt
Reescribe los .tf de la carpeta con el formato estándar: indentación de 2 espacios y los = alineados. No cambia lo que hace el código, solo cómo se ve. -recursive incluye las subcarpetas; -check solo avisa sin modificar (útil en CI).
terraform validate
Revisa que los archivos sean correctos: sintaxis, nombres de argumentos, tipos de valor y que las referencias apunten a cosas que existen. No se conecta a ningún servicio ni toca la infraestructura. Necesita haber hecho init antes.

Aplicar y borrar

terraform plan
Compara tus archivos con el estado y con lo que existe de verdad, y muestra qué haría: + crear, ~ modificar, - borrar, -/+ reemplazar. Termina con un resumen (Plan: 2 to add, 0 to change, 0 to destroy). No cambia nada: se puede correr siempre.
terraform apply
Calcula el plan, te lo muestra y espera a que escribas yes; cualquier otra respuesta cancela. Después crea, modifica o borra lo necesario y actualiza el estado. Si no hay diferencias, dice No changes y no hace nada.
terraform destroy
Borra todos los recursos registrados en el estado de esta carpeta (en un cloud, también sus datos). Muestra la lista y pide yes. Tus archivos .tf no se tocan: un apply vuelve a crear todo.
terraform plan -destroy
Muestra qué borraría destroy, sin borrar nada. Sirve para revisar antes de destruir un entorno.
3

plan y apply a fondo

Guardar el plan garantiza que se aplica exactamente lo que revisaste.

Planes guardados

terraform plan -out=tfplan
terraform apply tfplan
Guarda el plan en un archivo (tfplan) y después apply tfplan aplica exactamente ese plan, sin recalcular ni pedir confirmación. Así lo que se revisó es lo que se aplica, aunque alguien haya cambiado algo en el medio. Es el flujo habitual en equipos y en CI. No subas el archivo a Git: puede contener secretos.
terraform show tfplan
terraform show -json tfplan
Muestra en forma legible un plan guardado, por ejemplo para revisarlo antes de aplicarlo. Con -json lo devuelve en JSON, para que lo lea otra herramienta.
terraform apply -auto-approve
Aplica sin preguntar. ⚠ Usalo solo en automatización (CI) o en entornos descartables, nunca a mano en algo importante: no te deja ver el plan antes.

Pasar variables

terraform plan -var="entorno=dev"
Le da valor a una variable (variable "entorno") desde la línea de comandos. Tiene prioridad sobre los archivos .tfvars. Sirve para valores sueltos; para muchos, mejor un archivo.
terraform plan -var-file="prod.tfvars"
Carga los valores de las variables desde un archivo (nombre = valor, uno por línea). Se usa para tener un archivo por entorno: dev.tfvars, prod.tfvars. Usá el mismo -var-file en plan y en apply.
Sin -var: lee terraform.tfvars y *.auto.tfvars solos, y pregunta lo que falte. Orden completo en Variables y estado.

Planes parciales y especiales

terraform apply -replace="docker_container.chanchito"
Obliga a borrar y crear de nuevo ese recurso aunque no haya cambiado nada en el código, por ejemplo si quedó en mal estado. El plan lo muestra como -/+. Reemplaza al viejo comando terraform taint.
terraform plan -target="docker_container.chanchito"
Planifica solo ese recurso y lo que necesita, ignorando el resto. ⚠ Para emergencias (destrabar algo puntual), no para el día a día: deja el resto sin revisar y el estado puede quedar desparejo con tus archivos.
terraform apply -refresh-only
Lee cómo están los recursos de verdad y actualiza el estado para que coincida, sin cambiar la infraestructura. Sirve cuando alguien cambió algo a mano (drift) y querés aceptar ese cambio; después conviene ajustar también los .tf.
terraform plan -detailed-exitcode
Código de salida 0 = sin cambios, 2 = hay cambios, 1 = error. Útil en CI para detectar drift.
4

init: providers, módulos y backend

Volvé a correrlo cada vez que cambies providers, módulos o el backend.

Variantes de init

terraform init -upgrade
Actualiza providers/módulos a la versión más nueva que permitan tus restricciones (reescribe el lock file).
terraform init -reconfigure
Vuelve a inicializar ignorando la configuración de backend anterior. Se usa cuando cambiaste dónde se guarda el estado y no querés copiar el estado viejo (por ejemplo, porque apuntás a otro entorno).
terraform init -migrate-state
Cuando cambiaste el backend (por ejemplo, de archivo local a un bucket S3 o Azure Storage), copia el estado actual al nuevo lugar. Pregunta antes de copiar. Hacé una copia de terraform.tfstate antes, por las dudas.
terraform init -backend-config="backend-dev.hcl"
Completa la configuración del backend con valores de un archivo (nombre del bucket, ruta del estado…). Así el bloque backend del código queda genérico y cada entorno usa su propio archivo.

Providers y lock file

terraform providers
Muestra en forma de árbol qué providers necesita el proyecto, con qué restricción de versión y qué módulo los pide. Útil cuando init se queja de versiones incompatibles.
terraform providers lock -platform=windows_amd64 -platform=linux_amd64
Anota en .terraform.lock.hcl las huellas (hashes) de los providers para varios sistemas operativos. Sin esto, si generás el lock en Windows, el CI que corre en Linux puede fallar al verificarlo.
terraform get -update
Descarga o actualiza solo los módulos (no los providers). terraform init también lo hace; esto es más rápido si solo cambiaste la versión de un módulo.
5

Outputs, consola y grafo

Consultar lo que hay sin cambiar nada.

Outputs

terraform output
Muestra los valores de los bloques output (por ejemplo, la URL de la app o una IP), leídos del estado. Los marcados sensitive aparecen como <sensitive>.
terraform output -raw url
Muestra un solo output sin comillas ni formato, para usarlo en otro comando. Ejemplo en PowerShell: start (terraform output -raw url) abre la URL en el navegador.
terraform output -json
Todos los outputs en JSON, con su tipo, para que los lea otro programa (un script de CI, por ejemplo). Ojo: acá los sensitive sí aparecen en texto plano.
terraform show
Muestra el estado completo en forma legible: cada recurso con todos sus atributos (IDs, IPs, nombres). Con un archivo de plan como argumento, muestra ese plan.

Consola y grafo

terraform console
Abre una consola interactiva donde escribís expresiones de HCL y ves el resultado al instante, usando las variables y recursos reales del proyecto. Sirve para probar una función o una referencia antes de ponerla en el código.
> cidrsubnet("10.0.0.0/16", 8, 1)
"10.0.1.0/24"
> upper(var.entorno)
"DEV"
Ejemplo de sesión: cada línea con > es lo que escribís y debajo aparece el resultado. cidrsubnet calcula una subred dentro de un rango de IPs y var.entorno lee una variable del proyecto. Salís con exit.
terraform graph | dot -Tsvg > grafo.svg
terraform graph describe qué recurso depende de cuál, en el lenguaje de Graphviz; dot (un programa de Graphviz que hay que instalar aparte) lo convierte en una imagen. Útil para entender el orden en que Terraform crea las cosas.
6

state e import

Operaciones sobre el estado. Hacé un backup antes: terraform state pull > backup.tfstate.

Inspeccionar el estado

terraform state list
Lista todos los recursos que Terraform administra en esta carpeta, en la forma tipo.nombre (o module.x.tipo.nombre si están en un módulo). Lo que no aparece acá, Terraform no lo conoce.
terraform state show docker_container.chanchito
Muestra todos los atributos guardados de un recurso: ID, nombre, IP, puertos… Útil para saber un valor que generó el proveedor (como un ID) sin entrar a la consola web.
terraform state pull > backup.tfstate
Descarga el estado actual (sea local o de un backend remoto) y lo guarda en un archivo. Hacelo antes de cualquier operación delicada sobre el estado, como copia de seguridad.

Modificar el estado

terraform state mv docker_container.app docker_container.chanchito
Le cambia el nombre a un recurso dentro del estado, para que coincida con el nuevo nombre en el código, sin borrar ni recrear el recurso real. Hoy se prefiere un bloque moved { from = … to = … } en el código, que queda revisado en el plan.
terraform state rm docker_container.chanchito
Terraform deja de administrarlo; el recurso real sigue existiendo. Hoy existe el bloque removed.
terraform force-unlock <lock-id>
Con un backend remoto, Terraform bloquea el estado mientras alguien aplica, para que dos personas no lo modifiquen a la vez. Si un apply se cortó, el bloqueo puede quedar puesto; esto lo libera (el ID aparece en el mensaje de error). ⚠ Solo si estás seguro de que nadie más está aplicando.

Importar lo que ya existe

import {
  to = docker_container.monguito
  id = "<id-del-contenedor>"
}
Para que Terraform empiece a administrar algo que ya existe (creado a mano o por otra herramienta) sin recrearlo. to es el recurso del código y id, cómo lo identifica el proveedor (acá, el ID del contenedor). El próximo plan lo muestra como import y el apply lo agrega al estado.
terraform plan -generate-config-out=generado.tf
Junto con un bloque import, lee el recurso real y escribe en generado.tf el bloque resource correspondiente, para que no tengas que escribirlo a mano. Revisalo y limpiá los valores que no hagan falta.
terraform import docker_container.monguito <id>
La forma anterior de importar, por línea de comandos: el bloque resource tiene que estar escrito antes, y el cambio va directo al estado sin pasar por un plan. Se sigue pudiendo usar, pero el bloque import es más seguro.
7

Workspaces

Un estado separado por workspace, con el mismo código.

Comandos

terraform workspace list
Lista los workspaces: estados separados que usan el mismo código (por ejemplo, uno para dev y otro para prod). El que está en uso tiene *; default siempre existe.
terraform workspace new dev
terraform workspace select dev
new crea un workspace (con un estado vacío) y se cambia a él; select cambia a uno existente. terraform workspace select -or-create dev hace lo que haga falta. En el código, terraform.workspace devuelve el nombre del actual.
terraform workspace show
terraform workspace delete dev
show muestra el workspace en uso: conviene mirarlo antes de un apply. delete borra un workspace; solo deja si su estado está vacío (hacé destroy primero) y no podés borrar el que estás usando.

Usarlo en el código

locals {
  entorno = terraform.workspace   # "dev", "prod"…
}

resource "docker_container" "chanchito" {
  name = "chanchito-${terraform.workspace}"
  # ...
}
!

Es fácil aplicar en el workspace equivocado. Para dev/prod reales, mucha gente prefiere una carpeta por entorno (ver Módulos y proyecto).

Variables de entorno

Cambian el comportamiento de la CLI sin tocar el código.

Las más útiles

VariablePara quéEjemplo (PowerShell)
TF_VAR_<nombre>Valor de una variable de Terraform (ideal para secretos)$env:TF_VAR_mongo_password = "<password>"
TF_LOGLogs internos: TRACE, DEBUG, INFO, WARN, ERROR$env:TF_LOG = "DEBUG"
TF_LOG_PATHMandar esos logs a un archivo$env:TF_LOG_PATH = "tf.log"
TF_CLI_ARGS_planFlags extra para un comando$env:TF_CLI_ARGS_plan = "-parallelism=5"
TF_INPUT0 = no preguntar nada (CI)$env:TF_INPUT = "0"
TF_IN_AUTOMATIONSalida más corta pensada para CI$env:TF_IN_AUTOMATION = "1"
TF_DATA_DIROtra carpeta en vez de .terraform/$env:TF_DATA_DIR = ".tf-dev"
i

En Bash: export TF_VAR_mongo_password="<password>". Para borrarla en PowerShell: Remove-Item Env:TF_LOG.

9

CI, tests y extras

Lo que suele correr un pipeline.

Pipeline típico

# en cada pull request
terraform fmt -check -recursive
terraform init -input=false
terraform validate
terraform plan -input=false -out=tfplan

# al mergear a main
terraform apply -input=false tfplan
✓

fmt -check falla si algo no está formateado: buen primer filtro.

Otros comandos

terraform test
Ejecuta las pruebas de los archivos *.tftest.hcl: cada prueba hace un plan o un apply temporal con ciertos valores y verifica condiciones (assert). Lo que crea un apply de prueba se destruye al terminar.
terraform login
Abre el navegador para generar un token de HCP Terraform (el servicio de HashiCorp para guardar estados y ejecutar planes en equipo) o de un registro privado de módulos, y lo guarda en tu PC. No hace falta para trabajar en local.
terraform metadata functions -json
Lista en JSON todas las funciones de HCL que tiene tu versión de Terraform, con sus parámetros. La lista legible está en la documentación de Terraform y en Lenguaje HCL.
terraform -chdir=infra/dev plan
Ejecuta el comando como si estuvieras en otra carpeta, sin hacer cd. -chdir va antes del subcomando. Práctico en scripts o cuando el proyecto tiene una carpeta por entorno.
