Problemas comunes

Buscá por el texto del error. Cada tarjeta: qué ves → por qué pasa → cómo se arregla. Para más detalle: $env:TF_LOG = "DEBUG".

Dónde se rompe init validate y plan apply Estado

Antes de buscar: cómo diagnosticar

Comandos que aclaran la situación sin cambiar nada:

terraform validate
Revisa que los archivos estén bien escritos (sintaxis, nombres, tipos). Si falla acá, el problema está en el código.
terraform plan
Muestra qué haría. Si falla acá, suele ser un problema de credenciales, de conexión o de valores desconocidos.
terraform state list
Qué recursos administra Terraform según su estado.
$env:TF_LOG = "DEBUG"
Activa el registro detallado para el próximo comando (se desactiva con Remove-Item Env:TF_LOG).

Palabras que aparecen en los errores: refresh (leer el estado real de los recursos), lock file (versiones fijadas de providers), state lock (bloqueo del estado), drift (diferencia entre código y realidad).

La etapa en la que falla ya te dice de qué tipo es el problema.

1

init: providers y backend

No encuentra el provider

Error: Failed to query available provider packages
Could not retrieve the list of available versions for provider hashicorp/docker
Causa
Falta el required_providers y Terraform asume hashicorp/docker, que no existe. O hay un error en source, o no hay acceso a internet / proxy.
Solución
required_providers {
  docker = { source = "kreuzwerker/docker" }
}

El lock file no coincide

Error: Failed to query available provider packages
locked provider registry.terraform.io/hashicorp/aws 5.x does not match configured version constraint ~> 6.0
Causa
Cambiaste la restricción de versión pero .terraform.lock.hcl tiene la versión vieja.
Solución
terraform init -upgrade
Y commiteá el lock file actualizado.

Backend cambiado

Error: Backend initialization required, please run "terraform init"
Reason: Backend configuration block has changed
Causa
Modificaste el bloque backend (o pasaste de local a remoto).
Solución
# copiar el estado al nuevo backend
terraform init -migrate-state
# o empezar con el nuevo sin migrar
terraform init -reconfigure

Lock file sin hashes de otra plataforma

Error: Inconsistent dependency lock file
the cached package for registry.terraform.io/... does not match any of the checksums recorded
Causa
El lock se generó en Windows y el CI corre en Linux (o al revés).
Solución
terraform providers lock -platform=windows_amd64 -platform=linux_amd64
2

validate y plan

Referencia o argumento inexistente

Error: Reference to undeclared resource
A managed resource "docker_image" "app" has not been declared in the root module.

Error: Unsupported argument
An argument named "imagen" is not expected here.
Causa
Un nombre mal escrito, un recurso que se borró, o un argumento que no existe en esa versión del provider.
Solución
Revisá la documentación del recurso en el Registry para tu versión. terraform validate marca la línea exacta.

for_each con valores desconocidos

Error: Invalid for_each argument
The "for_each" set includes values derived from resource attributes that cannot be determined until apply
Causa
Las claves del for_each dependen de algo que se crea en el mismo apply (un ID, una IP).
Solución
Usá claves conocidas de antemano (nombres de variables, strings fijos) y dejá los valores desconocidos dentro de each.value.

for_each con una lista

Error: Invalid for_each argument
The given "for_each" argument value is unsuitable: the "for_each" argument must be a map, or set of strings, and you have provided a value of type tuple.
Solución
for_each = toset(var.nombres)

Ciclo de dependencias

Error: Cycle: docker_container.a, docker_container.b
Causa
A referencia a B y B referencia a A (directo o a través de otros recursos).
Solución
Cortá una de las referencias: sacá el valor a una variable o un local, o separá el recurso en dos.

Falta una variable obligatoria

Error: No value for required variable
The root module input variable "mongo_password" is not set
Solución
$env:TF_VAR_mongo_password = "<password>"
O un valor en terraform.tfvars (si no es secreto).

Credenciales del provider

Error: No valid credential sources found
Error: Cannot connect to the Docker daemon at unix:///var/run/docker.sock
Causa
AWS: no hay perfil ni variables de entorno. Docker en Windows: Docker Desktop cerrado o el provider apunta al socket de Linux.
Solución
# AWS
aws configure
$env:AWS_PROFILE = "<perfil>"
Docker: abrí Docker Desktop y usá host = "npipe:////.//pipe//docker_engine".
3

apply

El recurso ya existe

Error: Unable to create container: Conflict. The container name "/chanchito" is already in use
Error: creating S3 Bucket: BucketAlreadyExists
Causa
Existe algo con ese nombre que Terraform no administra (creado a mano, por compose o por otro estado).
Solución
Si es tuyo y lo querés administrar: importalo. Si sobra: borralo (docker compose down). Los buckets S3 tienen nombre global: elegí otro.
import {
  to = docker_container.chanchito
  id = "<id-del-contenedor>"
}

prevent_destroy frena el plan

Error: Instance cannot be destroyed
Resource docker_volume.mongo_data has lifecycle.prevent_destroy set
Causa
Está funcionando como debe: el plan quería destruir (o reemplazar) un recurso protegido.
Solución
Revisá por qué quiere destruirlo (¿un cambio que fuerza reemplazo?). Solo si de verdad querés borrarlo, sacá el flag a conciencia.

Permisos o cuotas

Error: AccessDenied: User ... is not authorized to perform: ec2:RunInstances
Error: ... quota exceeded
Causa
El usuario o rol con el que corre Terraform no tiene el permiso, o la cuenta llegó a su límite.
Solución
Agregá el permiso a la política del rol (el mensaje dice cuál) o pedí aumento de cuota. Después, apply otra vez.

El plan guardado venció

Error: Saved plan is stale
Causa
Alguien aplicó otro cambio entre tu plan -out y tu apply.
Solución
terraform plan -out=tfplan
terraform apply tfplan

Estado y drift

Error acquiring the state lock

Error: Error acquiring the state lock
Lock Info:
  ID:        6f1c2a…
  Who:       compañero@PC
  Operation: OperationTypeApply
Causa
Otro plan/apply está corriendo, o uno anterior se cortó (Ctrl+C, se cayó la conexión) y dejó el lock tomado.
Solución
Esperá. Si estás seguro de que nadie está aplicando:
terraform force-unlock <ID>

Alguien cambió algo a mano (drift)

Qué ves
Un plan sin cambios en el código propone modificar o recrear recursos.
Solución
Elegí quién tiene razón:
# el código manda: volver a lo declarado
terraform apply
# el cambio manual se queda: aceptarlo en el estado
terraform apply -refresh-only
…y después actualizá el código para que coincida.

El plan siempre muestra cambios

Causa
La plataforma normaliza un valor (mayúsculas, orden de una lista, JSON reformateado) o otra herramienta lo modifica después.
Solución
Escribí el valor tal como lo devuelve la API, o ignorá ese atributo:
lifecycle {
  ignore_changes = [tags["ultima_modificacion"]]
}

Renombré y quiere destruir

Causa
Para Terraform, cambiar el nombre local es borrar un recurso y crear otro.
Solución
moved {
  from = docker_container.app
  to   = docker_container.chanchito
}

Subí el estado a git

Causa
terraform.tfstate no estaba en el .gitignore.
Solución
Sacalo del repo y agregalo al .gitignore. Si el repo es público o compartido, rotá los secretos que tenía: siguen en el historial.
git rm --cached terraform.tfstate

Perdí el estado

Qué ves
El plan quiere crear todo de nuevo, pero los recursos existen.
Solución
Recuperá una versión anterior: terraform.tfstate.backup (local) o el versionado del bucket (S3/Azure/GCS). Si no hay copia, volvé a importar cada recurso con bloques import.

No encontré ese problema. Probá con otra palabra del error.
