Terraform · Cheatsheet 06

Práctica: tu app con Terraform y Docker

La forma más barata de aprender Terraform: el provider kreuzwerker/docker crea contenedores en tu Docker Desktop. Vas a levantar chanchito + monguito, lo mismo que hacía tu docker-compose.yml, con init → plan → apply.

Antes de empezar

Qué necesitás y qué términos aparecen en esta práctica.

Requisitos
Docker Desktop abierto (ver la hoja de Docker “Empezar desde cero”), Terraform instalado (paso 0 abajo) y una carpeta con la app: app.js, package.json y Dockerfile.
La app de ejemplo
Una API Node con Express y Mongoose que se conecta a Mongo con mongoose.connect("mongodb://mati:<password>@monguito:27017/miapp?authSource=admin"), escucha en el puerto 3000 y tiene las rutas / (lista) y /crear (crea un documento). Con cualquier app parecida funciona igual: lo importante es que el host de Mongo sea monguito y que la contraseña coincida con la que le pases a Terraform.
Provider de Docker
kreuzwerker/docker: el plugin que deja a Terraform crear imágenes, contenedores, redes y volúmenes en tu Docker local.
docker_image
Recurso que descarga una imagen o la construye a partir de un Dockerfile.
docker_container
Recurso que crea y arranca un contenedor (equivale a docker run).
docker_network / docker_volume
Una red para que los contenedores se encuentren por nombre, y un volumen para que los datos de la base sobrevivan.
npipe
Named pipe: el canal por el que, en Windows, los programas se comunican con el motor de Docker.
triggers
Valores que, si cambian, obligan a reconstruir un recurso. Acá: el contenido de app.js.
1

Cada parte del compose, en qué recurso se convierte

En Terraform nada es implícito: la red, el volumen y las imágenes son recursos propios.

✓

El contenedor de Mongo se sigue llamando monguito y está en la misma red: app.js se conecta igual que antes.

i

Las referencias (docker_network.app.name) le dicen a Terraform en qué orden crear todo. No hace falta ordenarlo vos.

!

Antes de empezar, bajá el compose (docker compose down): los nombres chanchito/monguito y el puerto 3000 no pueden estar ocupados.

2

Los archivos

Creá una carpeta terraform/ dentro de la carpeta de la app (al lado del Dockerfile).

versions.tf y providers.tf

terraform/versions.tf
terraform {
  required_version = ">= 1.11"

  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0"
    }
  }
}
terraform/providers.tf
provider "docker" {
  # Windows + Docker Desktop
  host = "npipe:////.//pipe//docker_engine"

  # Linux / macOS:
  # host = "unix:///var/run/docker.sock"
}
terraform/variables.tf
variable "mongo_user" {
  type    = string
  default = "mati"
}

variable "mongo_password" {
  type      = string
  sensitive = true   # se pasa con TF_VAR_mongo_password
}

variable "app_puerto" {
  type    = number
  default = 3000
}

main.tf y outputs.tf

terraform/main.tf
resource "docker_network" "app" {
  name = "chanchito-net"
}

resource "docker_volume" "mongo_data" {
  name = "mongo-data-tf"
}

resource "docker_image" "mongo" {
  name         = "mongo:7"
  keep_locally = true          # destroy no borra la imagen
}

resource "docker_image" "chanchito" {
  name = "chanchito:tf"
  build {
    context = "${path.module}/.."   # carpeta del Dockerfile
  }
  triggers = {                      # rebuild si cambia el código
    app = filesha1("${path.module}/../app.js")
  }
}

resource "docker_container" "monguito" {
  name    = "monguito"             # = host en app.js
  image   = docker_image.mongo.image_id
  restart = "unless-stopped"
  env = [
    "MONGO_INITDB_ROOT_USERNAME=${var.mongo_user}",
    "MONGO_INITDB_ROOT_PASSWORD=${var.mongo_password}",
  ]
  networks_advanced {
    name = docker_network.app.name
  }
  volumes {
    volume_name    = docker_volume.mongo_data.name
    container_path = "/data/db"
  }
}

resource "docker_container" "chanchito" {
  name    = "chanchito"
  image   = docker_image.chanchito.image_id
  restart = "unless-stopped"
  ports {
    internal = 3000
    external = var.app_puerto
  }
  networks_advanced {
    name = docker_network.app.name
  }
  depends_on = [docker_container.monguito]
}
terraform/outputs.tf
output "url" {
  value = "http://localhost:${var.app_puerto}"
}
3

Paso a paso

En PowerShell, desde la carpeta terraform/ de la app, con Docker Desktop abierto.

Levantar

# 0. Una sola vez: instalar Terraform
winget install Hashicorp.Terraform
Cerrá y abrí la terminal después.
# 1. Liberar nombres y puertos del compose
docker compose -f ../docker-compose.yml down
Sin -v: tus datos del compose quedan en su volumen.
# 2. La contraseña (la misma que usa app.js)
$env:TF_VAR_mongo_password = "<password>"
Dura lo que dura esa terminal.
# 3. Preparar, revisar y aplicar
terraform init
terraform fmt
terraform validate
terraform plan
terraform apply
El plan tiene que decir 6 to add. Confirmá con yes.

Probar, mirar y borrar

# 4. Probar la app
#   http://localhost:3000/crear  -> crea un documento
#   http://localhost:3000        -> lista
terraform output url
El output te recuerda la URL.
# 5. Lo que administra Terraform
terraform state list
docker ps
Los mismos contenedores, ahora creados por Terraform.
# 6. Borrar todo lo creado
terraform destroy
Borra contenedores, red y volumen (⚠ los datos de Mongo). Las imágenes quedan por keep_locally.
i

Se crean .terraform/, .terraform.lock.hcl y terraform.tfstate. Agregá al .gitignore del repo los que no van (ver Secretos y git).

¿Compose o Terraform?

Para correr apps en tu PC, Compose sigue siendo más simple. Esta práctica es para aprender el flujo de Terraform.

Comparación

Docker ComposeTerraform + provider docker
Levantardocker compose up -dterraform apply
Ver cambios antesNoSí: terraform plan
EstadoLo lee de DockerArchivo terraform.tfstate
Red y volúmenesAutomáticosRecursos explícitos
Desarrollo con recargaCómodo (bind mount + nodemon)Posible, pero incómodo
Mismo flujo para la nubeNoSí: cambiás el provider por aws, azurerm…
✓

Siguiente paso natural: el mismo proyecto en la nube, por ejemplo con el provider aws creando un bucket S3 o una instancia EC2 (ojo con los costos).
